# cardanoSignTransaction

## Requisitos [#requirements]

* Versiones mínimas de firmware
  * Touch: 4.1.0
  * Classic/Mini: 3.0.0

### Cardano: firmar una transacción <a href="#cardano-sign-transaction" id="cardano-sign-transaction"></a> [#cardano-sign-transaction-]

Solicita una firma de transacción. El usuario revisa y confirma la solicitud en el dispositivo.

```javascript
const response = await HardwareSDK.cardanoSignTransaction(connectId, deviceId, params);
```

### Parámetros <a href="#params" id="params"></a> [#params-]

[Parámetros comunes opcionales](/es/hardware-sdk/concepts/common-params)

Tipo CardanoSignTransaction

* `signingMode` - _obligatorio_ CardanoTxSigningMode
* `inputs` - _obligatorio_ `Array` de CardanoInput
* `outputs` - _obligatorio_ `Array` de CardanoOutput
* `fee` - _obligatorio_ `String`
* `protocolMagic` - _obligatorio_ `Integer` 764824073 para la red principal, 1 para la red de pruebas Preprod y 2 para la red de pruebas Preview
* `networkId` - _obligatorio_ `Integer` 1 para la red principal, 0 para la red de pruebas
* `ttl` - _opcional_ `String`
* `validityIntervalStart` - _opcional_ `String`
* `certificates` - _opcional_ `Array` de CardanoCertificate
* `withdrawals` - _opcional_ `Array` de CardanoWithdrawal
* `auxiliaryData` - _opcional_ CardanoAuxiliaryData
* `mint` - _opcional_ CardanoMint
* `scriptDataHash` - _opcional_ `String`
* `collateralInputs` - _opcional_ `Array` de CardanoCollateralInput
* `requiredSigners` - _opcional_ `Array` de CardanoRequiredSigner
* `collateralReturn` - _opcional_ CardanoOutput
* `totalCollateral` - _opcional_ `String`
* `referenceInputs` - _opcional_ `Array` de CardanoReferenceInput
* `additionalWitnessRequests` - _opcional_ `Array` de `string | Array<number>` (rutas). Se usa para solicitudes de testigos de multifirma y acuñación de tokens, ya que no pueden determinarse a partir de los parámetros de la transacción.
* `metadata` - _eliminado_ - usa `auxiliaryData` en su lugar
* `derivationType` - _opcional_ `CardanoDerivationType`: enumeración que determina el tipo de derivación usado. El valor predeterminado es ICARUS=1.
* `includeNetworkId` - _opcional_ `Boolean`. Determina si `networkId` debe serializarse explícitamente en el cuerpo de la transacción. El valor predeterminado es `false`.

#### CardanoTxSigningMode <a href="#cardanotxsigningmode" id="cardanotxsigningmode"></a> [#cardanotxsigningmode-]

**`ORDINARY_TRANSACTION`**

Representa una transacción de usuario ordinaria que transfiere fondos, delega participación o retira recompensas. Los testigos de la transacción se generan con claves derivadas de las rutas incluidas en `inputs`, `certificates` y `withdrawals`. Además, si hay acuñación de tokens, la transacción también incluirá testigos de las claves derivadas de las rutas incluidas en `additionalWitnessRequests`.

La transacción

* _debería_ tener una propiedad válida `path` en todos los elementos `inputs`
* _no debe_ contener un certificado de registro de pool
* _no debe_ contener `collateralInputs`, `collateralReturn`, `totalCollateral` y `referenceInputs`
* _debe_ contener rutas como credenciales de participación en certificados y retiros (no hashes de claves ni de scripts)
* _puede_ contener únicamente rutas 1852 y 1855
* _no debe_ contener solicitudes de testigos 1855 cuando la transacción no acuñe ni queme tokens

#### Particularidades del certificado de registro de pool de staking <a href="#stake-pool-registration-certificate-specifics" id="stake-pool-registration-certificate-specifics"></a> [#stake-pool-registration-certificate-specifics-]

OneKey permite firmar certificados de registro de pools de staking como propietario del pool. La transacción puede contener entradas externas (por ejemplo, del operador del pool), y OneKey no puede verificar si realmente lo son. Permitir la firma con una clave de gasto supondría el riesgo de perder fondos de una entrada que el usuario no pretendía gastar. También existe el riesgo de firmar involuntariamente un retiro incluido en la transacción. Para mitigar estos riesgos, incorporamos reglas especiales de validación para las transacciones de registro de pools de staking, que también se validan en OneKey. Las reglas son las siguientes:

1. La transacción no debe contener otros certificados, ni siquiera otro registro de pool de staking
2. La transacción no debe contener retiros
3. Todas las entradas de la transacción deben ser externas; es decir, path debe ser undefined o null
4. Debe proporcionarse exactamente un propietario como ruta de staking, y el resto como direcciones de recompensa codificadas en bech32

#### Registro de gobernanza (Catalyst y otros) <a href="#governance-registration-catalyst-and-other" id="governance-registration-catalyst-and-other"></a> [#governance-registration-catalyst-and-other-]

OneKey permite firmar transacciones con datos auxiliares que contienen un registro de gobernanza. Estos registros seguían anteriormente [CIP-15](https://cips.cardano.org/cips/cip15/), que ha sido sustituido por [CIP-36](https://cips.cardano.org/cips/cip36/). Actualmente, OneKey admite los formatos CIP-15 y CIP-36; el estándar previsto se puede especificar en el campo `format` (con CIP-15 como valor predeterminado). Difieren en lo siguiente:

* CIP-36 permite delegar el poder de voto en varias claves públicas de votación con distintos pesos (CardanoCVoteRegistrationDelegation), como alternativa a proporcionar una única clave pública de votación. El firmware de OneKey admite como máximo 32 delegaciones en un registro de gobernanza.
* Los registros CIP-36 contienen el campo votingPurpose. El valor 0 está destinado a la votación de Catalyst y el valor 1 a otros fines. Si no se proporciona ningún valor, OneKey serializa 0 de forma predeterminada (si se usa el formato CIP-36).

OneKey no admite actualmente las rutas de derivación 1694.

#### Resultado <a href="#result" id="result"></a> [#result-]

Desde que se incorporó la transmisión por partes de transacciones a la implementación de Cardano en OneKey por limitaciones de memoria, OneKey ya no devuelve toda la transacción serializada como resultado de la llamada `CardanoSignTransaction`. En su lugar, devuelve el hash de la transacción, los testigos y el complemento de datos auxiliares; el cliente debe ensamblar la transacción serializada.

Tipo CardanoSignedTxData

```javascript
{
    success: true,
    payload: {
        hash: string,
        witnesses: CardanoSignedTxWitness[],
        auxiliaryDataSupplement?: CardanoAuxiliaryDataSupplement,
    }
}
```
