# Developer Portal 1.2.0 Information Architecture

Audience: Hardware SDK maintainers reviewing how public developer docs should
work after the 1.2.0 Protocol V2 line. This is a working plan, not a public
page.

Last review: 2026-09-06
Current stable line: Hardware SDK `1.2.0` / `1.2.1` (public API). Internal
packages on `onekey` may already be `1.2.2-alpha.*`.

## 1. What this portal is

`packages/connect-examples/developer-portal` is the **public** integrator
site. It is not the same document set as repo-internal `docs/`.

| Surface | Reader | Job |
| --- | --- | --- |
| Developer Portal | Wallet / dApp / native host integrators | Choose a package, connect a device, call a public API, ship |
| `hardware-js-sdk/docs/` | SDK maintainers | Protocol, Core, Session, firmware internals |
| Package README | Package consumers in GitHub | Install and local-dev pointer |

Do not copy internal Core/Transport design docs into the portal. Translate
only the **public contract** that an integrator must follow.

## 2. What 1.2.0 changed for integrators

1.2.0 is the first stable Hardware SDK that speaks **Protocol V2** (OneKey
Pro 2, Neo) while keeping **Protocol V1** (Classic / Mini / Touch / Pro).

The public call shape did not become a new SDK:

```ts
HardwareSDK.method(connectId, deviceId?, params) → { success, payload }
```

What *did* change, and must be documented:

| Topic | Integrator-visible fact | Must not document as public |
| --- | --- | --- |
| Protocol | SDK detects V1/V2 from the live device. Do not branch on PID / BLE name / USB descriptor. | Probe order, Ping payload, frame CRC, seq |
| Devices | Pro 2 and Neo are first-class. Neo has no camera / Air-Gap. | `model_pro2` capability sharing internals |
| Device state | Prefer `getDeviceState()` as the V1/V2 read. `getFeatures()` stays compatibility. | Raw `DeviceInfoGet` / `DeviceStatusGet` |
| Wallet | New code should use `openWalletSession({ mode })`. Persist `deviceId + passphraseState`. | Firmware `session_id`, Core session store |
| Firmware | Pro → `firmwareUpdateV3`. Pro2/Neo → `firmwareUpdateV4`. Do not replay an update. | Host binding, prepared plan, romloader flash |
| Transport | Same WebUSB / BLE / low-level entries. V2 calls are serialized per device. | Link-fatal recovery internals |

## 3. Current portal problems

Observed on the 1.2.0 line, before this change:

1. **Version drift.** Changelog stops at `v1.1.21` (2024-12). iframe
   `connectSrc` still points at `https://jssdk.onekey.so/1.1.19/`.
2. **Missing devices.** Compatibility table and overview omit Pro 2 and Neo.
3. **Missing 1.2.0 public APIs.** No pages for `openWalletSession`,
   `getDeviceState`, `firmwareUpdateV4`.
4. **No first-run path.** Landing "Get Started" only scrolls. There is no
   `/hardware-sdk/getting-started`. Transport `index.mdx` is empty.
5. **Wrong knowledge lives in the wrong layer.** Protocol V2, wallet
   sessions, and Pro2 firmware live in internal `docs/` only. Integrators
   cannot discover them.
6. **Nav debt.** "Migration Gudie", lowercase "concepts", Hardware
   Integration dropdown only lists three transports.
7. **Two "session" words.** Agent Wallet session and hardware wallet session
   are different. They currently share vocabulary with no hardware page.

## 4. How the docs should work

Use Diataxis. Every new page must pick one job:

```text
Landing
  → Tutorial (Getting Started)
      → How-to (Transport / PIN / Passphrase / Firmware)
          → Explanation (Devices, Protocol, Wallet Sessions, Identifiers)
              → Reference (Basic / Device / Chain APIs)
```

Rules:

1. **One first-run path.** Getting Started is 5–10 minutes: install → init →
   search → first address. It does not explain Protocol V2.
2. **Same public API for V1 and V2.** Device-specific pages explain
   *constraints*, not a second SDK.
3. **Public contract only.** If an App should not call it, the portal should
   not document it as a method.
4. **EN and ZH ship together.** Do not leave a 1.2.0 page in one locale.
5. **Do not version-pin facts that drift.** Prefer "current stable 1.2.x"
   plus npm badges. iframe `connectSrc` must match the installed SDK.
6. **Internal docs stay the source for mechanism.** Portal pages link to
   public behavior and stop. Maintainers keep `docs/protocol`,
   `docs/device/wallet-session-and-security.md`, `docs/sdk/core-runtime.md`.

## 6. Phased delivery

### Phase 1 — this PR (make 1.2.0 tellable)

- Write this IA.
- Add Getting Started (EN/ZH) and point landing CTA at it.
- Add Devices, Protocol, Wallet Sessions concept pages.
- Add `openWalletSession`, `getDeviceState`, `firmwareUpdateV4` reference.
- Put Pro 2 / Neo on the device table.
- Refresh changelog and iframe version.
- Fix nav labels and add Getting Started to the Hardware dropdown.

### Phase 2 — follow-up PRs (quality of the path)

- Split Core API Guide: keep lifecycle here, move param tables toward
  reference pages.
- Write a firmware-update how-to that chooses V2 vs V3 vs V4.
- Document BLE reconnect / dispose at integrator level.
- Fill transport index as a chooser, not an empty hidden file.
- Correct `getPassphraseState` wording against the 1.2.0 contract
  (`passphraseState` is a wallet fingerprint, not a firmware session id).

### Phase 3 — hygiene

- Generate changelog from GitHub releases, or at least keep 1.2.x current.
- Inject iframe `connectSrc` from the published version instead of a
  hardcoded 1.1.19.
- Add Pro 2 / Neo device art instead of reusing Pro / Classic icons.
- Audit chain method pages for Pro2 field names (example: TON
  `signing_message`).

### Out of this track

- Landing visual redesign (`docs/landing-page-optimization-plan.md`).
- Agent Wallet content.
- Internal protocol / Core mechanism docs.

## 7. Page contract for new 1.2.0 pages

Each new page must answer:

1. When should I open this page?
2. What is the public API or decision?
3. What must I not do?
4. Where do I go next?

Do not paste Core sequence diagrams, protobuf field lists, or App-only host
bindings into the portal.

## 8. Success criteria

A new integrator on Hardware SDK 1.2.0 can:

1. Reach a copy-paste WebUSB path from the landing CTA in one click.
2. See Pro 2 and Neo in the device matrix, with protocol and Air-Gap truth.
3. Learn that V1/V2 is auto-detected and that they keep the same JS API.
4. Open a standard or hidden wallet without persisting `session_id`.
5. Pick `firmwareUpdateV3` vs `firmwareUpdateV4` by device family.
6. Read a changelog that includes 1.2.0.
