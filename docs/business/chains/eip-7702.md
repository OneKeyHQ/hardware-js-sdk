# EIP-7702 交易签名

> - 文档状态：当前 SDK 与 OneKey 固件实现
> - 最后代码核验：2026-07-15
> - 事实来源：`EVMSignTransaction`、EIP-7702 消息类型与 firmware-pro2 `sign_tx_eip7702.py`
> - 维护要求：授权结构、固件 delegator 白名单或 EIP-7702 消息变化后同步更新。

## 1. 交易结构

EIP-7702 交易在 EIP-1559 费用字段基础上增加 `authorizationList`。Hardware JS SDK 使用以下公共类型：

```ts
type EVMAuthorization = {
  chainId: number;
  address: string;
  nonce: string;
  addressN?: number[];
  yParity?: number;
  r?: string;
  s?: string;
};

type EVMTransactionEIP7702 = {
  to: string;
  value: string;
  gasLimit: string;
  nonce: string;
  data?: string;
  chainId: number;
  maxFeePerGas: string;
  maxPriorityFeePerGas: string;
  accessList?: EVMAccessList[];
  authorizationList: EVMAuthorization[];
};
```

调用入口仍是统一的：

```ts
HardwareSDK.evmSignTransaction(connectId, deviceId, {
  path: "m/44'/60'/0'/0/0",
  transaction,
});
```

`EVMSignTransaction` 通过非空 `authorizationList` 识别 EIP-7702。该交易还必须提供 `maxFeePerGas` 和 `maxPriorityFeePerGas`。

## 2. SDK 到 protobuf 的映射

当前 SDK 会：

1. 校验公共交易字段。
2. 将 `data` 按 1024 字节切出第一块。
3. 设置完整 `data_length` 和 `data_initial_chunk`。
4. 映射 EIP-2930 access list。
5. 映射授权列表中的 HD path 或外部签名。
6. 发送 `EthereumSignTxEIP7702OneKey`。
7. 根据 `EthereumTxRequestOneKey` 继续发送剩余 data chunk。

关键 protobuf 字段为：

```text
address_n
nonce
max_gas_fee
max_priority_fee
gas_limit
to
value
data_length
data_initial_chunk
chain_id
access_list
authorization_list
```

文档不复制完整 `evmSignTxEip7702` 源码；字段和分块行为以当前实现为准，避免示例随代码演进失真。

## 3. 授权签名来源

每个 authorization 支持两种签名来源：

### 设备生成授权签名

- 提供 `addressN`，设备使用该路径生成 authorization signature。
- 如果不提供 `addressN` 和外部签名，当前固件使用交易签名者的 `address_n`。

### 使用外部签名

- 同时提供 `yParity`、`r`、`s`。
- 固件校验 `yParity` 范围以及 `r/s` 的 32 字节长度。

同一个 authorization 不能同时包含 `addressN` 和外部签名。否则固件返回数据错误。

签名响应可能包含：

```ts
type EVMSignedTx = {
  v: string;
  r: string;
  s: string;
  authorizationSignatures?: EVMAuthorizationSignature[];
};
```

## 4. 当前固件限制

当前 firmware-pro2 对 EIP-7702 施加以下约束：

### 单条 authorization

```text
authorization_list.length == 1
```

空列表或多条列表都会被拒绝。虽然 SDK 公共类型是数组，调用方不能据此假设当前设备支持批量 authorization。

### chain ID

authorization 的 `chainId` 必须是：

- `0`，表示通配；或
- 等于交易的 `chainId`。

### nonce

- authorization nonce 必须小于 `2^64`。
- 当 authorization 没有外部签名且没有单独 `addressN` 时，固件要求 authorization nonce 等于交易 nonce 加一。

### 地址格式

- `authorization.address` 必须是带 `0x` 的 20 字节地址。
- 交易 `to` 必须是有效的 20 字节 EVM 地址。

## 5. Delegator 白名单与 calldata

当前固件只接受已注册 delegator：

| 名称       | 地址                                         | 初始 calldata 规则                |
| ---------- | -------------------------------------------- | --------------------------------- |
| Revoke     | `0x0000000000000000000000000000000000000000` | 撤销委托。                        |
| OKX        | `0x80296FF8D1ED46f8e3C7992664D13B833504c2Bb` | 第一块 data 必须等于 `8129fc1c`。 |
| MetaMask   | `0x63c0c19a282a1B52b07dD5a65b58948A07DAE32B` | 初始 data 必须为空。              |
| Simple7702 | `0x4Cd241E8d1510e30b2076397afc7508Ae59C66c9` | 初始 data 必须为空。              |

非白名单地址会返回：

```text
Authorization address not in registered delegators
```

对于非 revoke delegator：

- 有预设 initial data 时，`data_initial_chunk` 必须精确匹配。
- 没有预设 initial data 时，`data_initial_chunk` 必须为空。

这意味着当前实现不是一个可对任意委托合约和任意 calldata 进行盲签的通用 EIP-7702 签名器。

## 6. 用户确认与安全边界

设备会在交易签名前展示委托信息，包括：

- 当前发送账户。
- delegator 地址和已知名称。
- 是否为 revoke。
- EIP-7702 风险提示。
- 后续交易详情。

EIP-7702 的风险不只来自交易 `to`，还来自 `authorizationList.address`。应用 UI 必须同时展示：

1. 交易发送方。
2. 交易接收方 `to`。
3. delegator 地址。
4. authorization chain ID 和 nonce。
5. 是否由设备生成授权签名，还是使用外部签名。

不要把“delegator 位于固件白名单”解释为整个交易一定安全。白名单只限制委托代码目标，交易金额、接收方、data 和费用仍需用户确认。

## 7. Schema 与设备兼容性

- EIP-7702 使用 OneKey current Protocol V1/V2 schema 中的专用消息。
- legacy Trezor schema 当前不支持该消息，SDK 会明确报错，而不是静默改成其他交易类型。
- 设备支持仍受 `EVMSignTransaction.getVersionRange()` 和设备能力检查约束。
- 调用方应处理 `DeviceNotSupportMethod`、固件版本限制和设备数据校验错误。
