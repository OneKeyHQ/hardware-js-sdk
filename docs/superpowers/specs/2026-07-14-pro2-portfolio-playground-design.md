# Pro 2 Portfolio Playground Design

## Goal

Add a dedicated Expo Playground entry for validating the complete Pro 2 Portfolio transfer contract. The page accepts a server `packageBase64`, a local signed `.pfol` package, or a bundled development example, then invokes the SDK business API that stages and applies the package.

The page must never report success after file staging alone. Success requires the device to return `Success` for `PortfolioUpdate`.

## Scope

- Add a `/pro2-portfolio` route and sidebar entry.
- Support Base64, local PFOL file, and bundled example inputs.
- Preview the normalized package metadata before sending.
- Restrict execution to a connected Pro 2 device.
- Call `uploadPortfolio(connectId, { packageBytes })` exactly once per user action.
- Show transfer progress, final response, elapsed time, and actionable failures.
- Add focused tests for input parsing and the SDK two-phase transfer.

The page does not create, sign, or encrypt PFOL packages. Canonical development packages come from the firmware repository tooling. Production packages come from the Server signing service.

## Navigation

Add a dedicated `Pro 2 Portfolio` item next to the existing Pro 2 debug and update entries. A standalone page is preferred because Portfolio input selection, package inspection, progress, and device-apply semantics do not fit the generic method executor or firmware update page.

## Input modes

### Server Base64

The user pastes the Server `packageBase64` value. The page removes surrounding whitespace, decodes it into raw bytes, and rejects malformed or empty input.

### Local PFOL file

The user selects a `.pfol` file. The page reads the file as an `ArrayBuffer` and records the file name and byte length. The file picker is a convenience filter, not the only validation boundary.

### Bundled development example

The page provides:

- a readable Portfolio v1 JSON sample for schema inspection;
- a matching, development-signed PFOL binary generated by the firmware repository's canonical sender tooling.

The Playground must not reimplement OKAR packing, OKPP wrapping, Ed25519 signing, or key handling.

## Package preflight

Before enabling Send, perform lightweight host-side checks:

- package is non-empty and no larger than 64 KiB;
- leading container magic is `OKPP`;
- header type is `PFOL` when it can be read safely;
- display source, byte length, and a short hexadecimal prefix.

These checks catch obvious input mistakes only. They do not replace firmware signature, archive, version, or JSON validation.

## Transfer architecture

The page calls:

```ts
uploadPortfolio(connectId, { packageBytes })
```

The SDK owns the complete device protocol operation:

1. Write raw PFOL bytes sequentially with `FilesystemFileWrite`.
2. Use the fixed destination `vol1:/portfolio/portfolio.pfol.pending`.
3. Start at offset zero, use contiguous offsets, and wait for each `FilesystemFile` acknowledgement.
4. Use `overwrite=true` only for the first chunk and `append=false` for every chunk.
5. Send an empty `PortfolioUpdate` only after the staged response confirms all bytes.
6. Return success only after the device returns `Success` for `PortfolioUpdate`.

The page cannot configure the destination, offset, append mode, or protocol message order.

## UI states

The page represents these states explicitly:

- input selection;
- package ready;
- file staging in progress;
- device validation and apply in progress;
- complete;
- failed.

SDK device-progress events drive the file-staging progress indicator. The apply step remains active after staging reaches 100% and ends only with the `PortfolioUpdate` response.

The result card shows input source, package size, transport, elapsed time, and the final SDK payload. A successful file acknowledgement by itself is never shown as a completed Portfolio update.

## Device and retry behavior

- Require one selected, connected Pro 2 device.
- Disable duplicate Send actions while a request is active.
- Default to one transfer per click; do not add automatic repeat or stress-test controls.
- On write timeout or disconnect, instruct the user to reconnect and resend the complete package from offset zero.
- Do not implement resume from an assumed offset.
- A repeated `PortfolioUpdate` is firmware-idempotent, but the first Playground version keeps the public action at the full business-operation level.

## Error handling

Present distinct guidance for:

- malformed Base64 or unreadable file;
- invalid `OKPP` or `PFOL` preflight data;
- unsupported or non-Pro 2 device;
- `Invalid portfolio package` from firmware validation;
- `Unknown message type` for firmware without `PortfolioUpdate` support;
- file offset, size, timeout, and disconnect errors;
- general SDK or transport failure.

Do not fall back to writing `vol1:/portfolio/portfolio.pfol` directly.

## Internationalization

Add English and Chinese labels for the navigation entry, input modes, validation messages, execution states, result metadata, and retry guidance. Preserve unrelated existing locale edits and do not rewrite locale files wholesale.

## Testing

### SDK

- Verify the fixed `.pending` path and sequential file write.
- Verify `PortfolioUpdate` is sent only after the final file acknowledgement.
- Verify a staging failure prevents `PortfolioUpdate`.
- Verify the public API is exported and injectable.

### Playground

- Base64 decoding accepts valid input and rejects malformed or empty input.
- PFOL preflight accepts the expected `OKPP`/`PFOL` header and rejects invalid magic or excessive size.
- The page does not enable Send without a valid package and a connected Pro 2.
- Execution calls `uploadPortfolio` once and treats only its final success as completion.

## Out of scope

- Client-side PFOL signing or production key custody.
- Server Portfolio JSON construction and signing-service implementation.
- Automatic cooldown, content deduplication, or background App synchronization.
- Immediate Portfolio deletion or UI clearing.
- Repeated-transfer stress testing.
- Visual confirmation through framebuffer capture.
