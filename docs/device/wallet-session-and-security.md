# Wallet Session, Passphrase, and Attach-to-PIN

> Document type: Core mechanism
> Audience: Core, App wallet integration, and security reviewers
> Status: Compatibility migration in progress
> Code scope: `packages/core`, App wallet Session integration
> Last code verification: 2026-08-06
> Prerequisite reading: [SDK architecture overview](../architecture/overview.md)

## 1. Scope and Core Conclusions

This document explains how the current SDK handles Pro / Pro2 device initialization, passphrase, session_id, deviceId, and Attach to PIN. The focus is how the hardware stack collaborates end to end to manage sessions, not the parameter list of any single API.

The current code distinguishes five kinds of "session/identity":

| Name                         | Layer                                      | Meaning                                                                                      | Lifecycle                                         |
| ---------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| transport session / `mainId` | transport / Device                         | Connection handle used by the SDK and transport to occupy a device. On USB this is usually a bridge/webusb session; on BLE it is usually a uuid. | acquire until release                             |
| device `session_id`          | Firmware/SE + V1 Features / Pro2 DeviceSession | Identifier of the device-side passphrase/seed session, used to reuse an already unlocked wallet context. | Generated on the device; the SDK caches it in `DeviceWalletSessionStore` |
| `device_id`                  | V1 Features / Pro2 DeviceStatus            | Identifier of the current wallet initialization lifetime; not a physical serial number, and not a hash deterministically computed from the mnemonic. | Survives a normal reboot; changes after wipe / re-initialization |
| `serialNo`                   | Hardware identity                          | Hardware serial number used to identify the physical device; `KnownDevice.uuid` is only a historical compatibility alias. | Stable for the physical device                    |
| Protocol V2 frame `seq`      | hd-transport ProtocolV2Session             | V2 frame-level request sequence number, used for fragment/response tracking and log correlation. | Increments within the Cursor of each Transport/device key |

In one sentence: **the transport session answers "which device we are talking to", the device `session_id` answers "which passphrase context is currently unlocked on the device", `device_id` answers "whether we are still in the same wallet initialization lifetime", and V2 `seq` answers "which protocol call order this frame belongs to".**

### Current Public Contract

The following rules describe the SDK's current external behavior. The investigation notes and historical issue records retained later in this document only explain the design background:

- Protocol V1 obtains the wallet identifier through `GetPassphraseState`; when that is unsupported, it can fall back to a fixed testnet address.
- Pro2 / Protocol V2 first negotiates `eventless_wallet_session=true`; Ask only switches the wallet context and returns
  `Success`, while `DeviceSessionGet` obtains the current Session or tries to restore a specified Session. The SDK
  normalizes `btc_test_address` to `passphraseState`.
- Public `getPassphraseState()` remains the cross-protocol compatibility entry for existing Apps: V1 continues to send
  `GetPassphraseState`, while V2 maps inside Core to the new Ask/Get wallet Session flow.
- Protocol V1/V2 can both use the unified `openWalletSession()`, which explicitly distinguishes `standard`,
  `select-hidden`, and `resume-hidden`. The standard wallet uniformly returns `passphraseState=null`; a hidden wallet returns a
  non-empty `passphraseState` generated by the device. Wallet classification looks only at `walletType`. A hidden wallet's `passphraseState`
  can be combined with `deviceId` as a wallet binding; the firmware
  `session_id` is written only to the Core internal Store and does not enter the public response. Explicit `mode` is the only flow intent and must not be mixed with
  `useEmptyPassphrase/initSession`. TypeScript callers should use the SDK-exported
  `OpenWalletSessionMode.Standard/SelectHidden/ResumeHidden` to avoid maintaining protocol strings again in business code.
- Parameter validation errors are returned through a unified failure response
  `{ success: false, payload: { error, code } }`; when a required `resume-hidden` binding is missing, use
  `CallMethodInvalidParameter` and do not throw a bare exception with only a message to the caller.
- When `mode` is omitted, keep the old-parameter compatibility: `useEmptyPassphrase=true` enters the standard wallet; otherwise
  `initSession=true` re-selects a hidden wallet; otherwise a complete wallet binding resumes the hidden wallet, and with no binding hidden-wallet selection starts.
- Pro2 explicit resume maps the expected `passphraseState` to `DeviceSessionGet.btc_test_address`. When a local cache exists it
  also sends `session_id`; when there is no cache, firmware can first silently reuse the current SE Session by address, and if reuse is not possible
  complete the device-side passphrase flow. When the cache is rejected by firmware or the returned wallet does not match, the SDK still only accepts a
  final `passphraseState` consistent with the business binding. V1 still returns `WalletSessionInvalid` when there is no local Session cache.
- A successful Protocol V2 `DeviceSessionGet` response must contain both a non-empty `session_id` and
  `btc_test_address`; missing either field is treated as an incomplete protocol response and must not be recognized as a standard wallet.
- Protocol V2 empty-argument `DeviceSessionGet()` only reads the firmware's current wallet Session and does not guarantee that the current wallet is the standard wallet.
  When opening the standard wallet for the first time, call `DeviceSessionAskPin(Main)`, then after success call
  `DeviceSessionAskPassphrase` with an empty Host passphrase, then `DeviceSessionGet()`; when the cache is valid, first call
  `DeviceSessionGet(session_id, btc_test_address)` to resume. Core uses the returned real
  `btc_test_address` to build the standard-wallet internal index and does not introduce an SDK-invented `STANDARD_WALLET_KEY`.
- When Protocol V2 enters `select-hidden`, if live status clearly shows the device is already unlocked by Attach PIN, Core reads the current
  Attach PIN session and does not pop the passphrase UI (consistent with Pro1: the same PIN is already bound to that hidden wallet). To create a new
  passphrase hidden wallet, the user must first lock the screen, unlock with the main PIN, and then tap "+ Hidden wallet" again. Backfilling Cardano on an Attach PIN
  uses empty Host `AskPassphrase({ seed_domains: [Standard, Cardano] })`.
- V1 `Initialize.derive_cardano` remains per-call opt-in. V2 uses `DeviceSessionAskPassphrase.seed_domains`
  to decide which seeds are generated this time: wallet-open and non-Cardano calls send `[Standard]`; Cardano calls send
  `[Standard, Cardano]`. `DeviceSessionGet` neither carries nor generates Cardano (when passphrase is off, firmware
  Get will request Cardano itself). The `DeviceSession` response reports already-generated domains with the same enum. If Get shows Cardano is not yet
  present and the current call needs ADA: Attach PIN / standard wallet send Ask with an empty Host passphrase; hidden
  passphrase Ask again including Cardano, then Get. Before switching from Attach PIN to another non-empty passphrase wallet,
  the SDK will `lockDevice`, then throw `DeviceCheckUnlockTypeError`.
- The type of `DeviceSessionAskPin` is chosen by business intent: standard wallet and security operations use `Main`; when a normal business call already carries the target
  `passphraseState`, pre-unlock uses `Any`, allowing main PIN or Attach PIN to enter, then still validates the target hidden wallet with the returned
  `btc_test_address`; when the user explicitly chooses Attach PIN to open a hidden wallet, use `AttachToPin`.
  `unlockedAttachPin=true` only describes the current context and does not decide the PIN type of the next Ask.
- The old-parameter form `initSession=true` only invalidates the explicitly specified old wallet Session on the current device;
  mismatched wallet identifiers, device switches, and explicit `clearSessionCache()` also invalidate cache according to their own scopes.
- Pro2 Session capacity and eviction are managed entirely by hardware. The Core Store only saves
  non-authoritative restore handles of `deviceId + passphraseState -> sessionId`, does not copy hardware capacity policy, and does not implement LRU.
  When hardware judges a handle invalid, Core clears that entry and re-selects or unlocks according to the current public flow.
- When the caller provides an expected `passphraseState`, a first-result mismatch triggers one recovery corresponding to the wallet type; only if it is still inconsistent
  does it clear the current wallet cache and throw a wallet-state validation error.
- When Protocol V2 wallet identity is inconsistent, live status is refreshed; if the actual context was unlocked by Attach PIN, follow Pro V1's
  fail-closed policy: try to lock the device, clear the current wallet Session, and return
  `DeviceCheckUnlockTypeError`, without entering wallet re-selection. A non-Attach ordinary Session mismatch still allows one re-selection.
- When a Protocol V1 call carries `deviceId`, Core first validates live identity with an `Initialize` that does not include `session_id/passphrase_state`;
  only after they match is the wallet Session allowed to be reused, avoiding sending a Session from an old identity to the current hardware.
- After Pro2 unlock, wallet type is determined from the refreshed `passphraseProtection`, not from the pre-unlock snapshot.
- `clearSessionCache()` only clears SDK in-memory state and does not send a close-Session command to Pro1 or Pro2;
  providing `passphraseState` alone is a parameter error and will not clear the global cache.
- There is currently no independent requirement to "query which wallet the device currently has open"; `getDeviceState()` is only used to query
  Passphrase/Attach PIN capability and runtime status. The App treats the return value of `openWalletSession()` as the
  wallet-identity fact for this call, does not directly invoke unpublished low-level Session requests, and does not repeatedly open a wallet during page rendering.

The App may persist `deviceId + walletType + passphraseState` as a wallet reference; it must not save
`sessionId`, plaintext Passphrase, `initSession`, or this call's `resumed`. Sessions that the old CLI already wrote into the
OS Keychain can continue to be migrated and reused via `preloadSessionCache()`, but new wallet selection
will no longer obtain or persist the raw `sessionId`. When there is no old cache, the Core Store maintains Sessions only in-process; after an SDK
restart or Session invalidation, Pro2 explicit `resume-hidden` will re-select and validate the target wallet within the same call;
V1 still returns `WalletSessionInvalid` when it cannot resume safely.

## 3. Initialization Pipeline

### 3.1 Core Dispatch Entry

After a business API enters `callAPI()`, core extracts the following from the payload via `parseInitOptions()`:

- `initSession`
- `passphraseState`
- `deviceId`
- `deriveCardano`
- `connectProtocol`

These parameters are passed into `device.run(inner, runOptions)`. Initialization is therefore not scattered across business methods; it is uniformly controlled by `Device.run()`:

```text
callAPI
  -> findMethod / method.init
  -> DevicePool / DeviceList finds Device
  -> device.run(inner, runOptions)
  -> acquire
  -> initialize
  -> passphrase safety check
  -> method.run
  -> release or keepSession
```

This design exists because initialization involves device occupancy, the transport session, the features schema, passphrase state, and UI interaction. If every chain method handled this itself, it would be easy to leave a device unreleased, reuse the wrong session, or use stale features.

### 3.2 Pro / Protocol V1 Initialization

Pro currently still uses Protocol V1 initialization. The entry point is `Device.initialize()`:

1. If `initSession` is true, first call `clearInternalState(deviceId)` to clear the old session cache.
2. Look up the cache with `getInternalState()` using the current `passphraseState` and `deviceId`.
3. If a cache hit is found, put the cached device `session_id` into `Initialize.session_id`.
4. Also carry `passphrase_state`, `derive_cardano`, and `is_contains_attach=true`.
5. Call `Initialize -> Features`.
6. `_updateFeatures()` updates features; if a `session_id` is returned, write it back to the cache via `setInternalState()`.
7. Call `TransportManager.reconfigure()` based on features to select the appropriate V1 protobuf schema.

`is_contains_attach=true` is the SDK explicitly telling firmware that this initialization must include Attach to PIN related state. That lets features reflect extended fields such as `unlocked_attach_pin`, so the upper layer can tell whether the current unlock was an attach PIN unlock.

### 3.3 Pro2 / Protocol V2 Initialization

Pro2 does not use the traditional `Initialize/GetFeatures`. If `isProtocolV2()` is true in `Device.initialize()`, it takes a dedicated branch:

1. Write `this.passphraseState = options?.passphraseState`.
2. If `DeviceState` already exists and a forced new session is not required, reuse the cache; ordinary business calls do not read runtime status by default.
3. Otherwise call `_initializeProtocolV2()`.
4. `_initializeProtocolV2()` first sends `DeviceInfoGet`, then sends a
   `ProtocolInfoRequest` that always carries `eventless_wallet_session=true`.
5. In normal mode, if the capability list includes `DeviceStatusGet`, read live status; loader mode does not read status.
6. `DeviceStateMapper` merges the responses into a unified `DeviceState`; V2 does not construct a second public `Features` object.

Why Pro2 does not reuse V1 Initialize: Protocol V2 is currently a system-protocol capability, device information comes from `Ping + DeviceInfoGet`, and the documentation already states that V2 does not support traditional `GetFeatures`. The SDK uniformly outputs `DeviceState` so the business layer does not have to understand the raw V2 schema.

Note: the current implementation maps only the real `firmware-pro2` responses. `device_id` comes only from an explicit
`DeviceStatusGet` and is not filled in from `hw.serial_no` or a transport path. Initialization reads status only once in
normal mode according to capabilities; later ordinary business calls reuse `DeviceInfo/ProtocolInfo` and read
`DeviceStatusGet` only when runtime/status is explicitly refreshed.

## 4. deviceId and Device Identity Logic

### 4.1 Pro / Protocol V1

V1 `Features.device_id` represents the current wallet initialization lifetime. It is not a physical device serial number, and it is not an
identity deterministically computed from the mnemonic or seed; it stays the same across a normal reboot and is regenerated after wipe / re-initialization. It is therefore suitable for:

- Validating whether the `deviceId` specified by an API request still matches the current wallet initialization lifetime.
- Serving as the device key of `DeviceWalletSessionStore`, to avoid mixing sessions from different seeds.

When `BaseMethod.checkDeviceId` is enabled, core calls `device.checkDeviceId(method.deviceId)`. On mismatch it throws `DeviceCheckDeviceIdError`.

### 4.2 Physical Device Identity

In `Device.toMessageObject()`:

- On BLE, `connectId` uses `mainId` / uuid.
- On USB, `connectId` uses serialNo.
- `serialNo` uses the normalized physical device serial number.
- The deprecated compatibility field `uuid` temporarily returns the same serialNo.
- `deviceId` uses the current `features.device_id`.

The BLE scan phase of `searchDevices()` does not connect to the device just to read the serial number, so
`SearchDevice.serialNo` is null; the historical `uuid` at that stage may be a BLE Peripheral UUID /
Android MAC. Business routing uses `connectId`, and after device initialization `serialNo` is used as the hardware identity.

When `DevicePool` caches devices, it prefers `getCurrentSerialNo()` as the `devicesCache` key, and it also looks up old Device instances by descriptor `path`. That keeps "physical device cache" separate from "seed identity validation".

### 4.3 Pro2 / Protocol V2

The lifetime semantics of Pro2 `deviceId` match Pro. Pro2 firmware persists
`DeviceStatus.device_id` within an initialization lifetime and generates a new value on wipe / re-initialization. The SDK does not treat V2 `serial_no` as
`device_id`, because the two have different meanings:

- serialNo is physical hardware identity.
- deviceId is wallet-initialization-lifetime identity: stable across a normal reboot, changed after wipe / re-initialization.

When the device is locked or the current mode does not return `DeviceStatus.device_id`, the SDK leaves it empty or null and does not
fill it from serialNo, a transport path, or a BLE name.

## 5. device session_id Cache Logic

### 5.1 Cache Location and Keys

`DeviceWalletSessionStore` uses a primary map to store all wallet Sessions, and maintains an internal index for the standard wallet that points at the
real record in the primary map:

```text
deviceKey
├─ passphraseState -> sessionId
└─ standard -> { passphraseState, sessionId }  # internal index only, not a wallet identifier
```

`deviceKey` prefers the wallet-lifetime identity `deviceId`; when device identity is not yet established, the current physical-device cache key may be used.
The Store migrates existing Sessions only when a "temporary descriptor/path key is promoted to a formal `deviceId` for the first time".
If an already-stable identity changes from A to B, Core deletes A's Sessions and keeps B's existing cache; it never copies or overwrites B with A's
hidden-wallet Sessions.

Hidden-wallet `getInternalState()` has an important safety invariant:

```text
When this.passphraseState is absent, do not look up the session cache.
```

In other words, resuming a hidden wallet must carry `passphraseState` and must not scan other records. Explicit standard-wallet calls use
`getStandardInternalState()` to read the standard index, so the App does not need to pass
`passphraseState` back on later standard-wallet business calls. The Store can temporarily hold a pending Session that was just returned by the device but is not yet bound to a wallet identifier; the pending
state is used only for the same initialization pipeline and cannot be returned as a lookup result for an arbitrary wallet.

The primary map stores known `passphraseState -> sessionId` handles isolated by device, is not limited to the firmware's current capacity, and does not infer
hardware eviction order. When an existing wallet is updated, the latest firmware-returned `sessionId` overwrites the old handle; after firmware rejects a handle, only
the corresponding record is cleared. That way the SDK will not evict a still-restorable Session early by copying hardware-internal policy.

### 5.2 Why passphraseState Is Required

The old logic scanned `${deviceId}@*` when passphraseState was absent, which created two risks:

1. The user wanted the main wallet or an empty passphrase, but was routed to some hidden-wallet session.
2. Multiple hidden wallets existed under the same deviceId, and the SDK might reuse the wrong passphrase session.

The current policy is therefore: **a hidden wallet must be located by passphraseState; a standard wallet must be located by an explicit standard intent**.
V1/V2 `openWalletSession()` returns only the wallet identity `deviceId + passphraseState`. When the caller resumes a hidden wallet it
passes back only these two wallet-identity fields, and Core then reads the internal `sessionId`. The old CLI can restore a historical triple from its protected
OS Keychain and inject it into the Core Store via `preloadSessionCache()`; the SDK no longer exports `sessionId` through
public responses, and it does not accept it directly in a business API payload.

`DeviceSessionGet` requests and responses both sit on a sensitive logging boundary. Core does not log that call's payload,
and in particular must not output `session_id` or `btc_test_address` from the response.

### 5.3 Cache Write Entry Points

There are three main entry points:

1. `setInternalState(state, initSession)`
   Called after V1 `Initialize -> Features`. The cache is written only when `passphraseState` exists or `initSession=true`.

2. `updateInternalState(enablePassphrase, passphraseState, deviceId, sessionId, featuresSessionId, walletType)`
   Called after `getPassphraseStateWithRefreshDeviceInfo()`. Prefer the firmware-returned `session_id`; if none, use `features.session_id`.
   When `walletType=standard`, also update the standard-wallet internal index; other wallets still update only the primary map.

3. `preloadSessionCache(deviceId, passphraseState, sessionId)`
   Retained only so the old CLI can restore a historical complete triple from the OS Keychain; it is not part of App, web, plugin, or new
   wallet-selection flows.

`updateInternalState()` binds the final Session returned by the device to the real `passphraseState` and deletes the current device's pending Session, so an unbound state cannot continue to affect later requests.

### 5.4 Cache Clear Entry Points

1. When `initSession=true`, call `clearInternalState(deviceId)` before initialization.
2. When passphraseState validation fails, `checkPassphraseStateSafety()` calls `clearInternalState()`.
3. When a main-wallet request is unlocked via attach PIN, or the supplied passphraseState does not match the state unlocked by attach PIN, the device is locked and the session is cleared.
4. The App explicitly calls `clearSessionCache()` to clear one wallet, one device, or the entire SDK
   wallet Session cache according to the parameters.

When the standard wallet's real `passphraseState` is deleted, when an entire device is deleted, or when the full cache is cleared, the standard index is invalidated in sync; merely
replacing the standard-wallet Session does not delete hidden-wallet records on the same device.

The design goal of cache clearing is: once the actual device-side unlock state is found to be inconsistent with the caller's expectation, the SDK must not continue to trust the local session cache.

Parameter semantics of `clearSessionCache()`:

```ts
// Clear the entire SDK wallet Session cache
await HardwareSDK.clearSessionCache();

// Clear all wallet Session cache for a specified device
await HardwareSDK.clearSessionCache({ deviceId });

// Clear the specified hidden-wallet Session cache on a specified device
await HardwareSDK.clearSessionCache({ deviceId, passphraseState });
```

`clearSessionCache()` sets `useDevice=false` and will not acquire a device or send Protocol V1/V2 messages.
It only clears the single cache source `DeviceWalletSessionStore` and does not modify `DeviceState` or protocol raw snapshots. It is not equivalent to locking the device, canceling the current
request, or closing a Session that still exists in firmware/SE.

## 6. passphraseState Retrieval and Safety Checks

### 6.1 Protocol-Layered Wallet-Open APIs

Existing Apps can continue to use the compatibility `getPassphraseState()` on both Protocol V1 and V2; new callers should prefer
`openWalletSession()` to express wallet intent explicitly. Both entries set
`useDevicePassphraseState=false` to avoid triggering passphrase validation again while opening a wallet. V1
`getPassphraseState()` keeps the original parameterless firmware semantics; the V2 compatibility layer consumes
`useEmptyPassphrase/initSession` but does not write the caller's plaintext Passphrase or
`passphraseState` into the protocol request. Standard wallet, hidden-wallet selection, and explicit resume are still most complete under
the `mode` semantics of `openWalletSession()`.

1. The V1 compatibility entry calls `getPassphraseStateWithRefreshDeviceInfo()` with no parameters.
2. The V2 compatibility entry maps `useEmptyPassphrase=true` to a main-PIN standard wallet, and maps
   `initSession=true` to re-selecting a hidden wallet after clearing the old cache.
3. The unified entry maps `standard/select-hidden/resume-hidden` onto the V1 or V2 implementation.
4. When `mode` is omitted, normalize by the old-parameter priority: `useEmptyPassphrase=true` becomes `standard`;
   otherwise `initSession=true` becomes a new `select-hidden`; otherwise a complete wallet binding becomes `resume-hidden`, and
   no binding becomes `select-hidden`.
5. When old `initSession=true` also carries `passphraseState`, delete only the local Session on the currently connected device that corresponds to that
   `deviceId + passphraseState`; do not empty other hidden wallets on that device.
6. Every Protocol V2 / Pro2 wallet precheck sends
   `ProtocolInfoRequest { eventless_wallet_session: true }`. When opening the standard wallet for the first time: if passphrase is on then
   `AskPin(Main) -> AskPassphrase('', seed_domains) -> Get()`; if passphrase is off then
   `AskPin(Main) -> Get()`. When a cache exists, send
   `DeviceSessionGet(session_id, btc_test_address)`. Hidden-wallet resume carries `btc_test_address`; when selecting a new wallet
   it usually sends Ask first, then `DeviceSessionGet()` after success; if the device is already unlocked by Attach PIN, re-check
   live status and read the current `DeviceSession` directly, avoiding a passphrase UI or a repeated Attach PIN entry.
7. Firmware validates the current SE Session against `btc_test_address`, and for a Get that carries `session_id` tries to restore the specified Session.
   If the first `passphraseState` does not match, the standard wallet performs one
   `AskPin(Main) -> AskPassphrase('', seed_domains) -> Get()` (if passphrase is off, only AskPin then Get);
   a hidden wallet performs one unified wallet selection plus `Ask -> Get()`. Only if the second attempt still does not
   match is `DeviceCheckPassphraseStateError` thrown. The SDK does not actively `LockDevice` for ordinary expiry.
8. Pro2 hidden-wallet selection offers Host input, device input, and Attach PIN through a unified dialog. Host Passphrase is encoded as
   `{ passphrase, on_device: false, seed_domains }`, used only for the current blocking request, and is not cached, logged, or written into a wallet reference; device input
   is encoded as `{ on_device: true, seed_domains }` and does not carry plaintext. Attach PIN independently uses `DeviceSessionAskPin`;
   when Cardano is needed, send `AskPassphrase` with an empty Host passphrase and do not pop UI.
9. Pro2 firmware returns `DeviceSession`: `session_id` and `btc_test_address`; the SDK maps `btc_test_address` to the upper-layer `passphraseState`.
10. Pro V1 still uses `GetPassphraseState -> PassphraseState` and returns `passphrase_state/session_id/unlocked_attach_pin`.
11. If features show passphrase is not enabled but a state is now obtained, refresh device status as needed.
12. Call `updateInternalState()` to write the session cache.

For Pro / Pro2, the API response may still return
`passphraseState` even when `passphrase_protection` is not true. This is to support Pro-series passphrase / attach-to-pin semantics and must not simply reuse
the V1-device rule of "return state only when passphrase is enabled".

### 6.2 Support Detection

Protocol branches for low-level wallet-state retrieval:

- Protocol V2 hidden wallets use `AskPin/AskPassphrase -> Success -> DeviceSessionGet()`,
  while the standard wallet uses the main PIN context.
- Protocol V1 uses `GetPassphraseState` when features capability includes `Capability_AttachToPin`, or when the Pro firmware version is
  `>= 4.15.0`.

If a V1 device does not support the new interface, silently call Testnet `GetAddress` and use the returned address as passphraseState. This fallback applies only to V1 devices; Pro2 does not take this path.

### 6.3 Safety Checks Before Ordinary Business Calls

If an ordinary business method has `useDevicePassphraseState=true`, core performs two layers of checks:

1. `checkPassphraseEnableState()`

   - The device has passphrase enabled, but the call did not pass `passphraseState` and is not `useEmptyPassphrase`: throw `DeviceOpenedPassphrase`.
   - The device does not have passphrase enabled, but the call passed `passphraseState`: throw `DeviceNotOpenedPassphrase`.

2. `device.checkPassphraseStateSafety()`
   - Call `getPassphraseStateWithRefreshDeviceInfo()` to obtain the device's current real state.
   - If the supplied state does not match the state returned by the device, clear the cache and return false.
   - If the request is for the main wallet (`useEmptyPassphrase`) but the device was actually unlocked via attach PIN, lock the device and throw `DeviceCheckUnlockTypeError`.
   - If a hidden-wallet state is supplied but the state unlocked by attach PIN does not match, likewise lock and clear the cache.

The purpose of this layer is not "one more validation", but to prevent UI or cache from taking the user to the wrong wallet. In a hardware wallet, address derivation and signing are deterministic: once the passphrase context is wrong, the returned address or signature is still valid, but it belongs to another wallet.

## 7. Pro1 Passphrase and Attach to PIN Behavior Baseline

This section treats the existing behavior of OneKey Pro (hereafter Pro1, Protocol V1) as the Pro2 alignment baseline. First distinguish three credentials:

```text
Device main PIN
├─ Unlocks device access
└─ Does not directly decide which wallet is entered

Passphrase
├─ Participates in seed derivation and selects a hidden wallet
├─ Different passphrases correspond to different wallets
└─ An empty passphrase corresponds to the standard wallet

Attach PIN
├─ An independent PIN bound to a specific passphrase
├─ After entry, the device restores the corresponding hidden-wallet context
└─ Neither the device main PIN nor plaintext passphrase
```

The three can be understood as: the main PIN opens the device door, passphrase selects a safe inside the door, and Attach PIN is a shortcut key to one particular safe.

### 7.1 Main PIN Unlock and Wallet Selection Are Two Stages

Pro1 first completes device unlock via `UnLockDevice -> UnLockDeviceResponse`:

```text
Host                                      Pro1
  │                                         │
  │ UnLockDevice                            │
  ├────────────────────────────────────────>│
  │                                         │ Device shows main PIN entry
  │ UnLockDeviceResponse                    │
  │   unlocked                              │
  │   unlocked_attach_pin                   │
  │   passphrase_protection                 │
  │<────────────────────────────────────────┤
```

`UnLockDevice` only confirms device access and the unlock type; it does not guarantee that a hidden-wallet context has already been established. After unlock, `getPassphraseState()` still needs to be called so that `GetPassphraseState` triggers the real wallet selection and seed session establishment.

### 7.2 GetPassphraseState Request Semantics

Pro1 devices that natively support Attach to PIN use:

```text
GetPassphraseState {
  passphrase_state?: string
  _only_main_pin?: bool
  allow_create_attach_pin?: bool
}
```

- Ordinary hidden-wallet request: send a known `passphrase_state`; on first entry it is usually empty.
- Force standard wallet: send `_only_main_pin=true`, corresponding to the upper-layer `useEmptyPassphrase=true`.
- Allow creating an Attach PIN: send `allow_create_attach_pin=true`, corresponding to the upper-layer `allowCreateAttachPin=true`. This field only allows firmware to enter the creation flow; it does not mean the host creates the binding directly.

Pro1's passphrase input UI is not opened directly by request parameters. Instead, after firmware sends `PassphraseRequest` while establishing a seed session, the SDK and UI continue the interaction.

### 7.3 Ordinary Passphrase Full Flow

```text
App / CLI                  SDK                         Pro1 Firmware / SE
    │                       │                                  │
    │ getPassphraseState    │                                  │
    ├──────────────────────>│                                  │
    │                       │ GetPassphraseState               │
    │                       ├─────────────────────────────────>│
    │                       │                                  │ Check seed session
    │                       │ PassphraseRequest                │
    │                       │<─────────────────────────────────┤
    │ REQUEST_PASSPHRASE    │                                  │
    │<──────────────────────┤                                  │
    │                       │                                  │
    │ Choose input method   │                                  │
    ├──────────────────────>│                                  │
    │                       │ PassphraseAck                    │
    │                       ├─────────────────────────────────>│
    │                       │                                  │ Derive wallet and establish session
    │                       │ PassphraseState                  │
    │                       │<─────────────────────────────────┤
    │ passphraseState       │                                  │
    │ unlockedAttachPin     │                                  │
    │<──────────────────────┤                                  │
```

`PassphraseRequest` may carry `exists_attach_pin_user`, telling the SDK whether a selectable Attach PIN user currently exists. The SDK converts it into `UI_REQUEST.REQUEST_PASSPHRASE.existsAttachPinUser`.

The UI has three response modes:

```text
1. Host-entered passphrase
   PassphraseAck { passphrase: "..." }

2. Device-entered passphrase
   PassphraseAck { on_device: true }
   -> ButtonRequest_PassphraseEntry
   -> Device shows the passphrase input box

3. Use an existing Attach PIN
   Prerequisite: exists_attach_pin_user=true
   PassphraseAck { on_device_attach_pin: true }
   -> ButtonRequest_AttachPin
   -> Device shows the Attach PIN input box
```

A host-entered passphrase is first NFKD-normalized in the SDK, then written to `PassphraseAck.passphrase`. When device entry is selected, the host does not pass plaintext passphrase.

### 7.4 Three Paths: Standard Wallet, Hidden Wallet, and Attach PIN

Standard wallet:

```text
GetPassphraseState { _only_main_pin: true }
  -> Establish a seed session with an empty passphrase
  -> PassphraseState {
       passphrase_state: MainWalletState,
       session_id: MainSession,
       unlocked_attach_pin: false
     }
```

Ordinary hidden wallet:

```text
GetPassphraseState {}
  -> PassphraseRequest
  -> PassphraseAck { passphrase } or { on_device: true }
  -> Establish a hidden-wallet seed session
  -> PassphraseState {
       passphrase_state: HiddenWalletState,
       session_id: HiddenSession,
       unlocked_attach_pin: false
     }
```

Use an existing Attach PIN:

```text
GetPassphraseState {}
  -> PassphraseRequest { exists_attach_pin_user: true }
  -> PassphraseAck { on_device_attach_pin: true }
  -> ButtonRequest_AttachPin
  -> User enters Attach PIN on the device
  -> SE restores the passphrase bound to the Attach PIN
  -> PassphraseState {
       passphrase_state: HiddenWalletState,
       session_id: HiddenSession,
       unlocked_attach_pin: true
     }
```

### 7.5 Creating an Attach PIN

Creating an Attach PIN and using an existing Attach PIN are two different flows. The creation entry is explicitly authorized by the host:

Public callers should preferably enter the wallet-selection flow via `openWalletSession({ mode: 'select-hidden' })`, then
explicitly choose Attach PIN through `REQUEST_PASSPHRASE/uiResponse`. Compatibility `getPassphraseState()` on Pro2
can reuse the same UI selection channel, but it does not provide an explicit resume mode.

The conceptual device flow is:

```text
Select or enter the target passphrase
          │
          ▼
Establish and confirm the target hidden wallet
          │
          ▼
Device enters the Attach PIN creation flow
          │
          ▼
Verify the device main PIN / user authorization
          │
          ▼
Enter and confirm the new Attach PIN
          │
          ▼
SE securely stores the protected Attach PIN -> passphrase mapping
          │
          ▼
Return the final passphrase_state + session_id
```

The SDK does not store Attach PIN or passphrase mappings; mapping creation, verification, storage, and restore all belong to the firmware and SE security boundary.

### 7.6 PassphraseState and Session Cache

Pro1 finally returns:

```text
PassphraseState {
  passphrase_state
  session_id
  unlocked_attach_pin
}
```

- `passphrase_state` is a stable fingerprint of the current wallet, not plaintext passphrase. The SDK compatibility path uses a fixed BTC Testnet address as the state fingerprint.
- `session_id` is the device-side seed/passphrase session handle, used to reuse an already established wallet context.
- `unlocked_attach_pin` indicates whether the current context was restored via Attach PIN.

The SDK isolates sessions of different wallets with `deviceId + passphraseState`:

```text
DeviceWalletSessionStore
└─ deviceId
   ├─ MainWalletState    -> MainSession
   ├─ HiddenWalletStateA -> HiddenSessionA
   └─ HiddenWalletStateB -> HiddenSessionB
```

When `passphraseState` is not explicit, the SDK must not scan or reuse an arbitrary hidden-wallet session, to avoid routing a main-wallet request to the wrong hidden wallet.

### 7.7 Attach PIN Safety Checks

The core risk of Attach PIN is: the caller believes it is accessing the main wallet or hidden wallet A, but the device actually restored hidden wallet B via Attach PIN. The SDK therefore re-fetches the device's actual state and compares:

```text
Business request
  -> getPassphraseState
  -> Obtain actualPassphraseState + unlockedAttachPin
  -> Compare with expectedPassphraseState / useEmptyPassphrase

  ├─ States match
  │   └─ Continue to get address or sign
  │
  ├─ Main wallet requested, but unlockedAttachPin=true
  │   └─ lockDevice + clearInternalState + throw error
  │
  └─ Hidden wallet A requested, but the device returned hidden wallet B
      └─ lockDevice + clearInternalState + throw error
```

It is not enough to check only "whether the device is unlocked". A wrong passphrase context can still return a well-formed address and signature, but they belong to another wallet.

## 8. Attach to PIN Interaction Pipeline

### 8.1 protobuf Fields

V1 firmware schema fields related to attach-to-pin include:

- `Initialize.is_contains_attach`
- `Features.attach_to_pin_user`
- `Features.unlocked_attach_pin`
- `PassphraseRequest.exists_attach_pin_user`
- `PassphraseAck.on_device_attach_pin`
- `ButtonRequest_AttachPin`
- `GetPassphraseState.allow_create_attach_pin`
- `PassphraseState.unlocked_attach_pin`

Pro2 no longer uses the old `GetPassphraseState/PassphraseState`, and it does not depend on firmware
`PassphraseRequest/PassphraseAck/ButtonRequest/ButtonAck` intermediate states. The SDK collects device Passphrase/Attach PIN intent through existing UI Events,
then sends `DeviceSessionAskPassphrase` or
`DeviceSessionAskPin(AttachToPin)`; after Ask succeeds it uses `DeviceSessionGet()` to read the current Session; resume uses
`DeviceSessionGet({ session_id })`.
The final session comes from `DeviceSession.session_id`, and passphraseState comes from
`DeviceSession.btc_test_address`.

Pro2 status fields come from `DeviceStatus.passphrase_enabled`,
`attach_to_pin_enabled`, and `unlocked_by_attach_to_pin`. After a successful `DeviceSessionAskPin`,
Core refreshes `DeviceStatus` to confirm the actual unlock and wallet-feature status.

`attach_to_pin_enabled` tells the SDK whether to show an existing Attach PIN entry;
`unlocked_by_attach_to_pin` is used for the final safety check. Creating, updating, or deleting a binding still belongs on the device settings page and is not stuffed into a wallet
Session open request.

### 8.2 UI Event Flow

Protocol V2 wallet selection is initiated by the SDK with `REQUEST_PASSPHRASE` carrying `deviceOnly=false`, and
`existsAttachPinUser` tells the App whether to show Attach PIN. When the App returns a Host Passphrase it sends
`{ passphrase }`; when it returns `passphraseOnDevice` it enters device input; when it returns `attachPinOnDevice` it enters
Attach PIN. All three Ask paths return `Success`, after which Get reads the Session. Host Passphrase is handed to firmware only in that
interaction and does not enter logs, cache, or the public wallet Session response.
If the device is already unlocked by Attach PIN when `select-hidden` starts, that selection has already been completed on the device; Core no longer triggers
the UI/Ask path above, and instead re-checks `DeviceStatus` then reads the current Session directly.
`DeviceSessionAskPassphrase` must explicitly carry `on_device`: Host input sends
`{ passphrase, on_device: false }`, and device input sends `{ on_device: true }`.
Core performs idempotent NFKD normalization again, and rejects empty values, NUL, or Host Passphrases exceeding 50 UTF-8 bytes according to the firmware limit;
official App and Expo Playground forms further restrict this to 1–50 printable ASCII characters.
`session_id` on `DeviceSessionGet` is optional. With no ID it returns the current Session; with an ID it tries to restore; firmware always returns
the final actual Session, and the SDK compares `passphraseState` and decides whether to perform one restore.
Protocol V1 continues to keep the original
`PassphraseRequest -> PassphraseAck` behavior.

### 8.3 Attach PIN and Session Repair

The core risk of Attach to PIN is: the user apparently did not enter a passphrase manually, but the device has already switched to some hidden-wallet passphrase context according to the bound PIN.

Therefore, after obtaining the device session, the SDK must correct local state with the real `passphraseState/session_id` returned by firmware; attach PIN unlock status is provided by Pro2 `DeviceInfo.status.unlocked_by_attach_to_pin` or V1 `PassphraseState.unlocked_attach_pin`:

```text
DeviceSessionGet / GetPassphraseState
  -> DeviceSession(btc_test_address, session_id) / PassphraseState(passphrase_state, session_id)
  -> updateInternalState()
  -> DeviceWalletSessionStore.set(deviceId, passphraseState, session_id)
```

At the same time, before ordinary business calls, the passphraseState supplied by the caller is compared with the state actually returned by the device. If the hidden wallet unlocked by attach PIN does not match the caller's expectation, the SDK locks the device and clears the cache.

## 9. Pro2 Firmware / SDK Responsibility Boundary

Protocol V2 uses the boundary "Host explicitly chooses the entry, Firmware performs wallet switching on the device, Core validates identity":

| Capability          | Firmware / SE responsibility                 | SDK / Host responsibility                                              |
| ------------------- | -------------------------------------------- | ---------------------------------------------------------------------- |
| Standard wallet     | On AskMain, unlock or reset to the standard-wallet context as needed | Negotiate eventless; send AskMain, then read the actual Session via Get |
| Passphrase wallet   | Receive Host plaintext and switch the wallet context | Send a non-empty `passphrase`, then read the actual Session via Get; device-side input is explicitly unsupported |
| Use existing Attach PIN | Verify Attach PIN on the device and restore the bound Passphrase | Refresh status and validate `unlocked_by_attach_to_pin`                |
| Session get/resume  | Get with no ID returns the current Session; with an ID it tries to restore | Compare the actual `passphraseState`; restore at most once on mismatch |
| Wallet identifier   | Return the final `btc_test_address + session_id` | Map to `passphraseState + newSession` and validate the expected wallet |
| Main PIN / unlock   | Show PIN/fingerprint as needed, and return success or failure | Send `DeviceSessionAskPin` with an explicit type, then refresh status and read Session |
| Attach PIN binding management | Create, update, or delete bindings on the device settings page | Open the settings page and refresh status; do not stuff management actions into wallet Session requests |

`PassphraseAck` belongs only to the Protocol V1 firmware intermediate-request flow. Pro2's
split Session requests are protocol commands used by Core internally to select/resume a hidden wallet, not a public query API.
Host passphrase is first NFKD-normalized in Core; the result must be 1–50 legal UTF-8 bytes and must not contain
NUL or unpaired UTF-16 surrogates. This avoids JavaScript/Protobuf encoders replacing illegal strings and then entering
a wallet different from what the user typed.
Public `Features`, `DeviceState.raw`, device events, and logs must not contain `session_id`;
Sessions are stored only in the internal cache isolated by device and `passphraseState`.

## 10. Protocol V2 Transport Session and seq Management

### 10.1 Responsibilities of ProtocolV2Session

`ProtocolV2Session` is the unified session layer for V2 communication. Its responsibilities include:

- Increment `protoSeq` before each call, range 1-255, skipping 0.
- Encode the protobuf payload into a `0x5A` V2 frame.
- Call the transport's `writeFrame()` and `readFrame()`.
- Filter responses by expectedTypes / intermediateTypes.
- Serialize calls on the same session so two concurrent calls cannot consume each other's responses.
- The write phase has a watchdog; the read phase uses the call-specified timeout, and when unspecified uses a shared 5-minute cap,
  avoiding infinite waits while still allowing user confirmation and firmware install to set a more appropriate business timeout.

The `seq` here is a protocol frame sequence number and is not the same as the device `session_id`. It is used for V2 frame-level diagnostics and ordering control; the device wallet/passphrase session is still expressed by `session_id` in firmware messages.

### 10.2 Link Management in Transport

Current USB, WebUSB, and BLE Transports all manage V2 Links per device key through `ProtocolV2LinkManager`:

- Calls for the same device enter a serial queue so two requests cannot consume each other's responses.
- A Link reuses `ProtocolV2Session`, the frame assembler, and the platform adapter.
- `ProtocolV2SequenceCursor` continues to be retained after an ordinary Link fails, is released, or reconnects.
- Only Transport dispose clears the Cursor and all Link state.
- USB uses generation to isolate stale endpoint callbacks; the BLE adapter is responsible for notification, receiver, and native subscription cleanup.

All Transports use `ProtocolV2FrameAssembler` to reassemble a complete `0x5A` frame and to validate SOF, length, and CRC. The platform layer does not understand protobuf; it is only responsible for reliably transporting bytes. For the full lifecycle see [SDK architecture decisions](../architecture/decisions.md) and [Protocol V1/V2 transport](../protocol/protocol-v1-v2.md).

## 11. Firmware/SE-Side Session Source

The Pro2 submodule shows the low-level SE session handling:

- `handle_session_new()` calls `SE_CMD_SESSION_START` to generate a 32-byte session_id.
- `handle_session_open()` calls `SE_CMD_SESSION_OPEN` to open a specified session_id.
- The MicroPython extension `se_start_session()` will new + open when no session is open.

This shows that the device `session_id` is essentially a seed/passphrase session handle on the secure element/firmware side. The purpose of the SDK caching it is not to bypass safety checks, but to reuse a context the device has already established under the same passphraseState, reducing repeated passphrase entry or repeated initialization cost.

## 12. Typical Flows

### 12.1 Accessing a Hidden Wallet and Caching the Session

```text
App reads and caches protocol in the "open wallet" stage
  -> V1 temporarily keeps the App's existing Legacy wallet flow
  -> V2 calls openWalletSession(standard | select-hidden | resume-hidden)
  -> core finds Device
  -> Device.initialize()
  -> Pro2: AskPin/AskPassphrase (create) or DeviceSessionGet (resume) / Pro V1: GetPassphraseState
  -> Firmware returns passphraseState; session_id is written only to the Core internal Store
  -> SDK updateInternalState(deviceId, passphraseState, optional sessionId)
  -> App still identifies the wallet only by passphraseState; later business-call parameters stay unchanged
```

Later signing / get-address:

```text
App calls evmGetAddress({ passphraseState })
  -> Device.initialize({ deviceId, passphraseState })
  -> V1 first validates the live deviceId with Initialize that has no wallet-binding fields
  -> getInternalState() hits deviceId@passphraseState
  -> Only after V1 identity matches does the second Initialize pass through session_id/passphrase_state
  -> Pro2 later safety checks use DeviceSessionGet({ session_id })
  -> core then checkPassphraseStateSafety()
  -> method.run()
```

The App should not repeatedly execute `openWalletSession()` before every signer or address call. Migration happens only at the create,
resume, or switch-wallet stage: V1 keeps the original entry and parameters, V2 uses the unified entry. That way the App's existing
`deviceId + passphraseState` wallet key, warm-up initialization, and all business-command parameters do not need to change;
`sessionId` is still managed by Core's `DeviceWalletSessionStore` and does not enter public responses, the App's wallet primary key, or
`DeviceState`.

### 12.2 Requesting the Main Wallet While the Device Is Unlocked via Attach PIN

```text
App calls a business method({ useEmptyPassphrase: true })
  -> checkPassphraseStateSafety()
  -> Obtain the current device session / status
  -> Discover unlockedAttachPin=true
  -> SDK judges mainWalletUseAttachPin
  -> lockDevice()
  -> clearInternalState()
  -> Throw DeviceCheckUnlockTypeError
```

This is to avoid the user thinking they are in the main wallet while actually entering the hidden wallet bound to that PIN.

### 12.3 Attach PIN Unlocks the Wrong Hidden Wallet

```text
App calls a business method({ passphraseState: A })
  -> Obtain the current device session / status
  -> Firmware returns passphraseState B via attach PIN
  -> SDK judges A !== B
  -> lockDevice()
  -> clearInternalState()
  -> Throw an error or return passphrase state mismatch
```

This is to avoid a business request for one passphraseState reusing another hidden wallet's session.

## 13. Why It Is Designed This Way

### 13.1 Security First: Do Not Treat "Connected Successfully" as "Wallet Context Is Correct"

Hardware-wallet communication has multiple states: whether the device is connected, whether it has been acquired by the SDK, whether a PIN has been entered, which passphrase is current, and which seed is current. As soon as the passphrase context is wrong, addresses and signatures can still return successfully, but they correspond to the wrong wallet. Therefore the SDK must validate passphraseState before business calls.

### 13.2 User Experience: Reuse Sessions to Reduce Repeated Entry

`session_id` caching lets the same `deviceId@passphraseState` reuse a session already established on the device. For CLI, DApp, and mobile, this reduces repeated passphrase entry, especially for costly flows such as hidden wallets and Cardano derivation.

### 13.3 Compatibility: Pro / Touch / V1 Devices / Pro2 Protocol Coexist

The SDK needs to support all of the following at once:

- When a V1 device has no `GetPassphraseState`, the only option is the Testnet `GetAddress` fallback.
- New Pro V1 firmware supports Attach to PIN and needs `GetPassphraseState` plus extended fields.
- Pro2 V2 does not use `Initialize/GetFeatures/GetPassphraseState` firmware messages; it uses `DeviceInfoGet` and
  `DeviceStatusGet/DeviceSessionAskPin/DeviceSessionAskPassphrase/DeviceSessionGet`; Core exposes wallet semantics through both
  compatibility `getPassphraseState()` and explicit `openWalletSession()`.

The current implementation is therefore "V1/V2 compatible `getPassphraseState()` + V1/V2 explicit
`openWalletSession()` + protocol capability detection + state adapter", not hard-coding by device model alone.

### 13.4 Identity Isolation: serialNo, deviceId, and sessionId Must Not Be Mixed

serialNo stably points at hardware, deviceId points at the wallet initialization lifetime, and session_id points at the device-side unlocked session. Mixing them produces two kinds of problems:

- Using a session from an old seed on a new seed.
- Mistaking physical-device identity for seed identity, so that after a wipe it is still treated as the same wallet.

So even when Pro2 has a serialNo, it only accepts `DeviceStatus.device_id` as deviceId; the session cache
also prefers deviceId + passphraseState as the key.

### 13.5 Concurrency and Reliability: V2 Calls Must Be Serialized

Protocol V2 responses currently match mainly by type. If two calls run concurrently on the same session, one call may consume the other's response. `ProtocolV2Session.pendingCall` forces serialization so response ownership is determinate.

## 14. Current Implementation Notes

1. `getInternalState()` will not look up the session cache without passphraseState; this is currently the most important safety boundary.
2. Pro2 `DeviceInfoGet` uses the current firmware's real fields; `status.passphrase_enabled` maps to SDK `passphrase_protection`.
3. `supportProSeriesAttachPinPassphrase()` applies only to V1 Pro; unified
   `openWalletSession()` maps on V1 to the old Passphrase interaction and on Pro2 to
   the split Ask/Get wallet flow.
4. Business methods such as settings, firmware, files, and device-status classes usually set `useDevicePassphraseState=false` to avoid triggering passphrase validation pointlessly.
5. As long as a wallet business method accepts `deviceId`, it must enable live device-identity checks; Protocol V1 must not pass through a cached Session before identity is confirmed.
